# Как работать в пространстве Borshkit

Borshkit — рабочее пространство, где «готово» ещё не значит «принято». Принимает Borshkit — по доказательствам, привязанным к точному состоянию файлов. Где доказательства быть не может, принимает человек.

## Основной сценарий: текущий харнес

Пользователь говорит обычным языком. Работай инструментами уже открытого Claude/Codex; для этого не нужен дополнительный исполнитель, отдельная модель или вложенный агент. Сначала получи `borshkit обзор --json`, покажи задачу, этап, последнее событие и следующее действие. В терминале `borshkit` открывает меню. Роли — рекомендации по работе, не ограничения личности текущего агента.

Не запускай фоновые процессы ради статуса. Дополнительных исполнителей, worktree, монитор и MCP запускай только по отдельному выбору. Нагрузка и количество подключённых исполнителей — разные вещи. `обзор --json --resources` измеряет зарегистрированные процессы по запросу; CPU — накопленное время, RAM — наблюдение. Внешние MCP принадлежат харнесу. `обзор stop <id>` запрашивает остановку своей работы; завершение подтверждается отдельно.

Настройки меняются через предложение. Перед применением вызови `borshkit обзор review-settings <id> --json`, покажи изменения и последствия, спроси пользователя средствами харнеса «Применить эти изменения?» и дождись явного ответа. Только после согласия: `borshkit обзор apply-settings <id> --host claude|codex|vscode --digest <digest> --decision apply --json`. Не придумывай согласие. Доверие обеспечивается разрешениями основной среды; этот вызов не является криптографическим доказательством действия человека. Изменение предложения требует нового согласия.

## С чего начать

1. Прочитай `borshkit/START-HERE.md` и `borshkit/STATUS.md`.
2. `borshkit статус` — режим приватности, задачи, что ждёт человека.
3. `borshkit знания контекст <задача>` — что в проекте связано с задачей.

## Правила

- **Не правь** `borshkit/settings/`, доказательства (`borshkit/tasks/*/evidence`, `logs`) и историю пространства. Настройки меняются предложением: `borshkit настройки предложить файл.json --от <твоё имя исполнителя>`; ослабление защиты подтверждает только человек.
- **Не объявляй задачу принятой.** Запусти проверки: `borshkit задача проверить <задача>`, затем `borshkit задача итог <задача>` и покажи человеку лист `acceptance.md`.
- Критерии классов: `auto` — решает проверка; `model` — твоё мнение, PASS требует доказательства `file:line`; `manual` — слепая зона, решает человек. Если что-то не проверено — так и говори: «не проверено».
- **Исследование:** каждый источник сохраняй командой `borshkit материал добавить …` (файл, `--url`, `--текст`, `--через jina`, `--команда`) и цитируй как `(источник: m-…, «точная цитата»)`. Источник, прочитанный в обход Borshkit, проверка цитат отклонит.
- **Git:** обычная отправка `git push` требует поручения пользователя и разрешений основного харнеса. Не делай `git reset --hard`, `git clean -f`, `git branch -D`, принудительную отправку. Для человека есть `borshkit что-изменилось`, `кто-что`, `вернуть`, `собрать`, `отправить`.
- **Приватность:** не читай и не выводи секреты (`.env`, ключи). В строгом режиме ничего не отправляй наружу без явного «да» человека.

## Дополнительные команды по явному выбору

- `borshkit роли` — роли команды и их навыки: `architect`, `implementer`, `ui-engineer`, `reviewer`, `simplicity-reviewer`, `designer`, `ios-designer`, `motion-reviewer`, `a11y-reviewer`, `researcher`, `tester`, `docs-writer`, `readme-designer`, `attribution-steward` и другие.
- `borshkit работа запустить <задача> --роль <роль> --исполнитель <имя> | --пул <пул>` — поручить работу исполнителю. Пишущие роли работают в отдельной копии проекта.
- `--навыки пакет/навык` — добавить к работе навык из `borshkit навыки` (например, `emil/animate`). Добавляй только то, что нужно задаче: больше текста не значит лучше результат.
- `borshkit библиотека [категория]` — проверенные первоисточники для интерфейса: Apple HIG, WCAG, WAI-ARIA APG, компоненты, анимация. Ссылайся на них, а не на память.
- `borshkit вопросы` — открытые вопросы. Критические решает только человек.

## Дополнительная команда и расширенные средства

Сначала прочитай SETUP.md, TEAM.md и STATUS.md. Операционный сценарий описан в docs/guide/team-operations.md пакета. Координатор планирует зависимости, инженер поставки готовит среду, независимый security-reviewer проверяет критерии. `стенд запустить` может расходовать платные ресурсы; нужен явный выбор модели и набора. `бюджет` учитывает резервы, UNKNOWN не снимается без владельца. `монитор` запускается только явно и предлагает изменения без применения. Passkey подтверждает только связанное действие после доверенного сопряжения; агент не регистрирует себя владельцем. Импорт переносимого набора не принимает результаты и не возобновляет процессы.
