Приёмка по целям#

Коротко: ты задаёшь цели и критерии. Что можно проверить автоматически, Borshkit проверяет сам. Остальное превращается в короткий список «что посмотреть тебе». Итог — лист приёмки.

Три класса критериев#

Класс Кто решает Пример
auto проверка: тесты, сборка, линтер или встроенная проверка Borshkit «Сборка и тесты проходят»
model модель-ревьюер, но с ограничениями (ниже) «Переключатель подписан и доступен с клавиатуры»
manual ты «После перезапуска тема осталась тёмной»

auto#

Критерий выполнен, когда все его проверки дали PASS на текущем состоянии. Хотя бы один FAIL — критерий не выполнен. Проверка не запускалась или устарела — «не проверено».

Встроенные проверки Borshkit:

  • citations — цитаты в отчёте исследования есть в сохранённых источниках, дословно (Исследования);
  • attribution — у каждого чужого источника есть благодарность, лицензия и ссылка;
  • readme-assets — картинки README на месте, с подписями (alt) и не слишком тяжёлые.

model#

Модель-ревьюер отвечает PASS, FAIL или UNKNOWN и должна указать доказательство: файл и строку или команду.

  • FAIL возвращает задачу на исправление.
  • PASS закрывает критерий сам, только если для его метки (tag) есть твоя цель доверия, она подтверждена измерением для этого семейства моделей, и даже пессимистичная оценка ошибки укладывается в цель. Пример: цель «не больше 5 % ложных PASS» требует около 73 сравнений с человеком без единой ошибки — 0 из 20 ещё допускают до 16 % (borshkit оценка доверие).
  • Без такой цели PASS модели — это пункт листа «посмотри сам».
  • Ревью от того же семейства моделей, что и автор, независимым не считается: пункт ждёт тебя. Авторами считаются все пишущие исполнители задачи, включая тех, кто начал работу и упёрся в лимит.
  • Ревью привязано к состоянию, которое видел ревьюер, когда начинал. Если файлы изменились, пока он работал, ревью устарело сразу.
  • Ревью, импортированное из файла (задача отзыв), может вернуть задачу на исправление, но его PASS остаётся пунктом для тебя: Borshkit не видел, на каком состоянии и кем оно сделано. Так же — ревью от неизвестного семейства моделей.

manual#

Слепая зона: автоматически не проверить. В контракте ты описываешь шаги, что должно быть видно и где смотреть. В листе это превращается в инструкцию. Ответ даёшь командой:

sh
borshkit задача подтвердить тема C3 да "видел тёмную тему после перезапуска"

Итог задачи#

Статус Что значит
🟢 принято все цели достигнуты, состояние не менялось во время сверки
🟡 автоматически ок, ждёт тебя всё, что можно, доказано; остались пункты для человека
🔴 нужно исправить есть FAIL или правки вне границ задачи
⚪ не проверено для части критериев нет действующих доказательств

Политика приёмки в контракте:

  • mixed (по умолчанию) — принято, когда достигнуты все цели;
  • auto — то же, но Borshkit предупредит, если есть критерии, которые не проверить автоматически;
  • manual — даже при достигнутых целях итог подтверждаешь ты: borshkit задача принять <задача>.

Границы задачи#

В контракте есть paths — какие файлы задача может менять. Если работа изменила что-то за этими границами, итог — 🔴, и в листе видно, какие файлы. Файлы, изменённые ещё до начала задачи, не считаются. В проекте без Git изменения находятся по хешам файлов, записанным при создании задачи. Файлы, которые возвращает API-исполнитель, Borshkit вне границ вообще не записывает.

Сборка: принимается то, что попадает в основную версию#

borshkit собрать <задача> переносит работу из копии задачи в основную версию. Это возможно, только если:

  • задача принята;
  • в копии нет несохранённых правок (иначе принято не то, что лежит в её истории);
  • копия уже содержит текущую основную версию проекта.

Если основная версия ушла вперёд, сначала borshkit задача обновить <задача>: она вольётся в копию, доказательства устареют, и проверки с приёмкой пройдут заново — уже на объединённом состоянии. Изменения, которые объединяются без конфликта, но вместе ломают поведение, так становятся видны до сборки.
