Реализация, автоматические тесты и живые испытания — разные уровни доказательств. Модели и физические устройства ждут пользовательских испытаний. Cline API не предоставляет достоверные статус и отмену. Исторические обсуждения ниже объясняют решения своего времени; текущие возможности сверяй по архитектуре и roadmap.

## Как всё связано

```mermaid
flowchart LR
  you(["Ты: цель"]) --> task["Задача<br/>цели и критерии"]
  task --> job["Работа<br/>роль + исполнитель"]
  team["Команда<br/>модели + оценки + ресурсы"] --> plan["План: предложено"]
  task --> plan
  plan --> applied["Настройки: применено"]
  applied -->|отдельная команда запуска| job
  job --> copy["Копия проекта<br/>ветка borshkit/…"]
  copy --> checks["Проверки<br/>тесты, сборка, citations"]
  checks --> ev["Доказательства<br/>для точного состояния"]
  job -. ревью .-> ev
  ev --> sheet["Лист приёмки"]
  sheet -->|пункты для тебя| you
  sheet -->|🟢 принято| merge["собрать → отправить"]
  kb[("Знания<br/>заметки + SQL")] -. контекст .-> job
  sheet -. уроки .-> kb
```

## Как устроена эта документация

Каждая страница — заметка в формате Borshkit: сверху frontmatter с `bk-type` и связями (GitHub показывает его таблицей), внизу раздел «Связи» с обычными ссылками. Поэтому одни и те же файлы:
- читаются на GitHub как обычный Markdown;
- открываются в Obsidian как граф;
- собираются Borshkit в SQL ([граф](graph/README.md)).

Подробнее — в заметке [База знаний](concepts/knowledge.md).
