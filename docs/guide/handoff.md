# Передать работу другому харнесу

Сегодня доступны три разных механизма: `handoff.md` и `handoff.json` при критической остановке работы, экспорт инструкций среды и перенос явно выбранных файлов. Они не переносят активный сеанс модели, ключи, процессы или доверие к прежним проверкам.

## Короткий пакет для нового чата

Сохрани текст вне чата и сверяй его с репозиторием перед продолжением:

```text
Задача: dark-mode; цель и критерии: <ссылка на contract.json>
Репозиторий, ветка, базовый SHA, текущий SHA: <точные значения>
Границы: <paths и что не входит>
Сделано: <файлы и решения с причинами>
Проверено: <команда, результат, SHA, ссылка на лог>
Не проверено / блокеры: <факты отдельно от гипотез>
Следующий шаг: <одно конкретное действие>
```

Убирай повторения, длинные логи и историю обсуждения. Оставляй решения, точные ссылки, ошибки и неизвестное. Сначала цель и состояние, затем доказательства, затем следующий шаг. Не превращай сжатое резюме в доказательство: новый харнес должен прочитать контракт и проверить актуальность файлов.

## Реальные команды

`borshkit интеграция export --host codex` создаёт инструкции для Codex; допустимые имена: codex, claude, gemini, copilot, roo, cline. Если файл уже содержит свои инструкции, автоматической перезаписи нет.

Команды переноса и точный синтаксис см. в [справочнике](../reference/commands.md). Набор ограничен 32 MiB, содержит явные файлы и шаблон настроек, проверяется на целостность и возможные секреты. Импорт не перезаписывает файлы и не применяет настройки. На новой машине нужны новые пробы и проверки.

Контекст базы знаний по задаче ограничен бюджетом. Diff ревьюера имеет отдельный приоритет в общем пакете. Полное автоматическое сжатие и единая схема передачи между всеми харнесами остаются [планом](../roadmap.md).
