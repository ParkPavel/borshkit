# Borshkit (Борщкит) — Modular AI Workspace

Анализ источников и проектная спецификация (черновик v6). Рабочее название TaskWeave заменено на **Borshkit** решением владельца D22.

Дата анализа: 2026-10-05; v2–v6 — 2026-10-06, после ответов владельца (§2). Во время анализа исходные репозитории не изменялись; они клонировались только для чтения, тесты Claudex запускались локально. Реализация начата с версии 0.1.0 (см. README, раздел «Что уже работает»).
Обозначения: **[Ф]** — проверенный мной факт (файл/команда), **[А]** — заявление авторов, не проверенное мной, **[В]** — мой вывод, **[?]** — неизвестно.

## 1. Что есть в источниках (реализовано vs заявлено)

### 1.1 Claudex — ядро приёмки (≈3,9 тыс. строк JS в `src/`+`bin/`, без runtime-зависимостей)

Реализовано и покрыто тестами [Ф]:
- **Контракт задачи** — `src/tasks.mjs` `validateContract`: цель, non-goals, решения, пути, критерии с типами доказательств (`automated|source|ui|persistence|review`), проверки, связанные с критериями, DAG подзадач; `analyzeContract` — предупреждения о расплывчатых критериях, плейсхолдерах, непокрытых критериях.
- **Привязка доказательств к состоянию** — `src/io.mjs` `snapshot()` (HEAD + sha256 содержимого tracked+untracked файлов), `runtimeDigest()` (код, роли, скиллы, профиль, локальная конфигурация); `verifyTask` помечает `CURRENT|STALE`; `convergeTask` выдаёт `PASS|FAIL|UNKNOWN` по критерию и понижает всё до UNKNOWN, если состояние изменилось во время сведения.
- **Схема результата** — `config/result.schema.json`; `src/adapters.mjs` `validateResult`: пропущенный критерий → UNKNOWN + `resultGaps`, PASS без evidence отвергается.
- **Разделение завершения и приёмки** — `COMPLETED` ≠ `proposedAcceptance` ≠ acceptance (`docs/explanation/architecture.md`, «Job state and evidence»).
- **Адаптеры** — только Claude Code и Codex CLI (`src/adapters.mjs`), проверка флагов через `--help` до запуска; Codex — только read-only; Claude-writer — только `Read,Glob,Grep,Edit,Write`, без shell и MCP. Для установленного здесь Claude Code 2.1.289 все требуемые флаги (`--restricted`, `--safe-mode`, `--tools`, `--strict-mcp-config`, `--json-schema`) присутствуют в `--help` [Ф]; Codex CLI не установлен → [?].
- **Права** — режимы `full|scoped|approval` (`src/config.mjs`), одноразовые одобрения (`src/approvals.mjs`), claims путей (`src/claims.mjs`), worktree для writer (`src/worktrees.mjs`).
- **Явное переключение провайдера** — `src/modes.mjs`: передача ролей по записи с «долгом» перепроверки.
- **Жизненный цикл jobs** — `src/jobs.mjs`: очередь, readiness по событию провайдера, таймауты, отмена, postmortem, классификация отказа (QUOTA и др.).
- Hooks Claude Code (`src/hooks.mjs`): SessionStart, Stop/SessionEnd, PreToolUse(Bash), UserPromptSubmit.
- Guards публикации (`src/security.mjs`), `retro` (`src/retro.mjs`), граф кода (`src/graph.mjs` + vendored Graphify), профиль Obsidian (`src/obsidian.mjs`, `profiles/obsidian.json`).

Ограничения [Ф/В]:
- `snapshot()` вызывает `git rev-parse HEAD` → **задачи вне Git не поддерживаются**.
- Провайдеры захардкожены (две ветки `if` в `prepareAdapter`); ролей 9 (`config/roles.json`).
- `vendor/graphify` — **73 280 строк Python** (в 19 раз больше ядра) с двумя локальными патчами; в git закоммичены **69 файлов `__pycache__/*.pyc`** — дефект гигиены.
- `library/apple-hig` без лицензии — не распространяется (`library/README.md`), корректно исключён из git.

Заявления, которые я не могу проверить [А]: «202 jobs рабочего журнала», «семь кросс-модельных раундов ревью» (`CHANGELOG.md` 1.0.0) — журнал приватный. Сравнительного бенчмарка нет — авторы признают это сами (`docs/research/validation.md`, «Current limits»).

### 1.2 ECC — большой мульти-харнесс дистрибутив контента

Факты [Ф]: 3043 коммита с 2026-01-17 (410 — с 2026-09-01); 293 `SKILL.md`, 68 агентов, 94 команды; 38 модулей установки и 7 профилей (`manifests/install-modules.json`, `install-profiles.json`: minimal, core, developer, security, research, full, opencode); цели — Claude, Codex, Cursor, OpenCode, Gemini, Qwen, Zed и др.
- **Hooks**: 24 записи в `hooks/hooks.json` — PreToolUse ×9 (в т.ч. `observe-runner` на **каждый** вызов инструмента, `config-protection`, `gateguard`), Stop ×7 (в т.ч. блокирующий `stop-format-typecheck`, timeout 300), SessionStart ×2 (загрузка «предыдущего контекста»), PreCompact, PostToolUse, SessionEnd.
- **Верификация** — инструкции тому же агенту: `skills/verification-loop/SKILL.md` (агент сам пишет PASS/FAIL-отчёт), `skills/delivery-gate/SKILL.md` (regex по транскрипту, mtime, свободное место на диске). Привязки к снапшоту, состояния UNKNOWN и независимого ревьюера нет [Ф/В].
- **Память/обучение** — `hooks/memory-persistence/`, `scripts/memory.js`, continuous-learning; дефолтный модуль `workflow-quality` уже включает `council-multi-model`, `dev-team`, `continuous-learning*` [Ф].
- **Selective install** — install-state со стабильными ID, sidecar `hooks.metadata.json` с fingerprint, idempotent update/uninstall (`hooks/README.md`) — **хорошая идея для пакетов**.
- `src/llm/` — Python-абстракция провайдеров (claude, openai, ollama, atlas, astraflow; ~1,6 тыс. строк) с `supports_tools()`.
- `ecc2/` — Rust control plane, авторы сами называют «alpha… not the finished product» [Ф].
- Происхождение скиллов: `origin: ECC` — 202, `community` — 43, отдельные сторонние авторы; явное поле `license` — только у 18 из 293 [Ф]. Есть модули, связанные со спонсорами (`ito-compute`) и коммерческий слой (ECC Pro).
- Заявления «production-ready» (`AGENTS.md:3`), «agent harness operating system» (README) — [А].

### 1.3 Каталог бесплатных API — данные, а не runtime

[Ф]: README генерируется `src/pull_available_models.py` (нужны API-ключи провайдеров); 13 «free»-провайдеров и 13 с trial-кредитами; поля — лимиты и список моделей. **Нет** машиночитаемых полей tool calling, structured output, политики данных; конфиденциальность упомянута только текстом в отдельных разделах (`README.md:81`, `:109` — обучение на данных / opt-in в training). Без лицензии копировать данные нельзя — только ссылаться.

## 2. Решения владельца (2026-10-06), принятые как исходные данные

| # | Решение | Следствие для архитектуры |
|---|---|---|
| D1 | Настройки самой среды меняет отдельный **доверенный агент**, как правило выбранная пользователем подписочная модель | Конфигурация — защищённый ресурс; остальные исполнители её только читают (§4) |
| D2 | Три **режима приватности**: умеренный, строгий, экспериментальный | Фильтр исходящих данных, «чистая комната» для агентов, журнал ключей сессии (§5) |
| D3 | Приёмка **автоматическая** там, где это возможно; слепые зоны выдаются как **инструкция для ручной приёмки** | ADR-004 Claudex пересматривается; классы критериев (§6) |
| D4 | Borshkit — **новый, более свежий продукт**, рабочая среда для любого проекта с низким порогом входа | Новый репозиторий; Claudex — источник кода и истории решений (`lineage.md`), не зависимость |
| D5 | Сопровождающий — **1 человек** | Жёсткий отбор объёма; внешние индексаторы вместо собственного мультиязычного парсинга |
| D6 | Вместо Graphify нужна **связанная база знаний проекта** (документация + код) для обучения и самоподдерживающегося контекста | Новый компонент ядра (§7) |
| D7 | Отдельная **уточняющая сессия по инструментам** пространства | Повестка — §19 |
| D8 | Пространство разворачивается **как мод** для Claude Code и других систем; взаимодействие понятно даже ребёнку | Плагин + `AGENTS.md`; принципы прозрачности (§10) |
| D9 | Обучение — **для всех**: людей и агентов; граф читается через **Obsidian**; новый обобщённый стандарт документации «SQL + wikilinks» | База знаний = хранилище Markdown-заметок с wikilinks (источник истины) + производный SQL-индекс (§7) |
| D10 | Приёмка — **смешанная или автоматическая при достижении целей, которые задаёт пользователь** | Цели приёмки — часть контракта; `model`-критерии могут закрываться автоматически, если цель пользователя по качеству подтверждена измерением (§6) |
| D11 | Публичные данные не считаются персональными; контрибьюторов референс-проектов **нужно указывать** | Класс данных `public-attribution` разрешён во всех режимах (§5); отдельная роль атрибуции (§9) |
| D13 | **Локальный запуск**: из корня проекта виден весь обзор — база знаний, задачи, **собственные настройки**; папка автоматически в gitignore | Папка пространства `borshkit/` в корне проекта, хранилище Obsidian целиком; правило Claudex «состояние вне checkout» заменяется на «состояние в игнорируемой папке» (§10.1) |
| D14 | Указывать **всех** контрибьюторов референс-проектов | Полный сгенерированный список + компактная сетка в README (§9) |
| D15 | Изображения по умолчанию — **через Codex** (по словам владельца, у него есть доступ к GPT Image); плюс выбор из бесплатных API с **автоматическим переключением при лимитах** | Пулы исполнителей с политикой переключения (§4.3); прежнее «никакого автоматического fallback» заменено на «переключение только внутри пула, разрешённого пользователем и режимом приватности» |
| D16 | Подключить **Agent Reach** для `researcher` | Внешний инструмент сбора с интернета; захват каждого источника в материалы (§8.1) |
| D17 | **Локальный git** внутри `borshkit/` нужен; поверх git — **оболочка для новичка**, объясняющая, что это такое | История пространства в отдельном локальном репозитории; словарь, точки возврата и обучение внутри `borsch` (§10.2) |
| D18 | Переключение исполнителей разрешено **для всех ролей**, но нужна ясная **картина фонового статуса**: кому ушло, кто работает | «Диспетчерская» — экран, строка статуса, заметка в Obsidian; авторство каждого изменения в локальном git (§4.3, §10.3) |
| D19 | Agent Reach — **все доступные ресурсы** | Все каналы доступны к подключению; каналы со входом в аккаунт настраивает сам пользователь, cookies остаются у инструмента, получение — на стороне `borsch` (§8.1) |
| D20 | Резервная копия истории пространства — **вопрос остаётся открытым**, позже выносится на обсуждение на GitHub | Запись в §18 «открыто для обсуждения»; по умолчанию резервной копии нет |
| D21 | **Стандартный тайминг 1 минута**; в режиме **автопилота** — автопринятие ответа по умолчанию; **критический вопрос** — остановка с отчётом, ожиданием, сохранением прогресса и передачей контекста; звуки — уведомлениями основного CLI | Режим автопилота, классы вопросов, критическая остановка (§10.4) |
| D22 | Название — **Borshkit (Борщкит)**, лозунг — **Modular AI Workspace** | Переименование пакета, плагина, папки и команды (§10.5) |
| D12 | Нужна **команда полного цикла** с кросс-модальными ролями, включая «ленивого сеньора» (ponytail), оформителя README с изображениями (через Codex), стюарда этики и благодарностей GitHub | Каталог ролей, привязанный к capabilities исполнителей и проверкам (§8, §9) |

| Оркестрация ECC (tmux/worktree, council, dev-team) | ECC | **Исключить** | Второй координатор = дублирование | — |
| Память / continuous learning | ECC | **Не брать**; «самоподдерживающийся контекст» строится в базе знаний из проверенных артефактов (§7), а не из транскриптов | Запись каждого вызова инструмента конфликтует с режимами приватности и актуальностью | — |
| `src/llm` | ECC | **Не использовать** (только как референс) | Python, спонсорские провайдеры, тесты не прогонялись | MIT |
| `ecc2` | ECC | **Исключить** | Alpha по словам авторов | MIT |
| Сбор данных из интернета для `researcher` | Agent Reach (`agent_reach/`, `skill/SKILL_en.md`) | **Подключить извне** как необязательный инструмент: фиксированная версия, установка только через предложение `configurator`, без его автообновления; Borshkit владеет захватом источников (§8.1) | ~7,3 тыс. строк Python; маршрутизатор и установщик сторонних CLI (OpenCLI, yt-dlp, twitter-cli, mcporter, gh…), «never a wrapper» (`docs/install.md`) | MIT; условия использования площадок — на пользователе |
| Каталог API | raullenchai / Jun Siang Cheah | **Только ссылка-источник для поиска**; собственный реестр провайдеров с `verifiedAt` | Нет лицензии, данные устарели, нет нужных полей | нет лицензии |

**Дублирование при совместной установке Claudex-подобного ядра и ECC** [В]: SessionStart (снапшот-сводка vs «предыдущий контекст»), Stop (сводка vs 7 гейтов), проверка завершения (`converge` vs `verification-loop`/`delivery-gate`/`santa-method`), worktrees (`src/worktrees.mjs` vs модуль `orchestration`), память (`.local/` состояние vs `memory`/`homunculus`), установка (`setup` vs `install-apply` + install-state), учёт стоимости (`retro` vs `cost-tracker`/`evaluate-session`), секреты (`scan` vs `pre-bash-commit-quality`/AgentShield), роли (9 ролей vs 68 агентов).

**Единственный владелец координации: ядро `borsch`.** Только оно создаёт задачи, выдаёт jobs, хранит доказательства и записывает решение о приёмке. Исполнители (CLI-агенты, API, локальные модели) получают ограниченный пакет и возвращают результат по схеме; их внутренние субагенты ядру не видны и состоянием задачи не владеют. Для ревьюеров вложенные агенты отключаются (как в Claudex для Codex).

**Совместимость** [В]:
- *Skills*: формат Agent Skills (`SKILL.md` + frontmatter) общий для Claudex и ECC → контент переносим; активация и бюджет контекста — нет, проверять оценкой.
- *Hooks*: оба пишут в `.claude/settings*.json`; одновременная установка без арбитра даёт конфликт семантики. Borshkit устанавливает свои hooks только с собственными стабильными ID и отказывается ставить их поверх чужих Stop-блокировок без явного согласия.
- *Память*: в Borshkit памятью являются контракты, материалы и доказательства; разговорная память не является источником истины.
- *Конфигурация*: общий контракт в репозитории Borshkit; машинное — в игнорируемой папке `borshkit/` в корне проекта (§10.1).
- *Права*: обеспечиваются флагами исполнителя (структурно); hooks и правила — второй, советующий слой.
- *Жизненный цикл*: состояния job из Claudex (`QUEUED…COMPLETED|FAILED|TIMED_OUT|CANCELLED`) + отдельная приёмка задачи (`PASS|FAIL|UNKNOWN` + решение человека).

## 4. Исполнители и доверенный агент настройки

### 4.1 Классы исполнителей

| Класс | Примеры | Свой tool loop / sandbox | Роль в MVP |
|---|---|---|---|
| CLI-агент по подписке | Claude Code, Codex CLI | да / да (контролируется флагами) | `configurator` (доверенный), `implementer`, `reviewer` |
| API-модель | Anthropic/OpenAI API, OpenAI-совместимые бесплатные tier'ы | нет | только read-only `reviewer`/`researcher` **на переданном материале** |
| Локальная модель | Ollama, llama.cpp, LM Studio (OpenAI-совместимый endpoint) | нет | как API; основной вариант для строгого режима без договора с провайдером |

Если API-модели нужны инструменты, её запускают через CLI-агент с поддержкой OpenAI-совместимого endpoint, а не через собственный tool loop Borshkit. Флаги таких CLI я не проверял → [?], адаптер делает probe.

**Манифест исполнителя** (`schemas/executor.v1.json`), заполняется probe-командой и человеком, не каталогом:
`toolCalling: native|none`; `structuredOutput: json_schema|json_mode|none` (reviewer требует одно из первых двух + локальную `validateResult`); `sandbox`; `quota` с `source` и `verifiedAt`; лимит → переключение внутри пула или отказ, если пула нет (§4.3); `dataPolicy: trains|no-train|unknown` с источником (`unknown` = `trains`); `cost`; `trusted: bool`; **`modalities`**: вход (`text`, `image`) и выход (`text`, `code`, `image`) — по ним назначаются кросс-модальные роли (§8). Генерация изображений через Codex: по словам владельца, есть доступ к GPT Image [А]; мной не проверено, подтверждается probe на E4. Ручная смена провайдера — записанной передачей роли с долгом перепроверки (`src/modes.mjs`).

### 4.2 Доверенный агент настройки (D1)

- **Что защищено:** `workspace.json` (исполнители, роли, режим приватности, профили, пакеты, режим доступа), установленные hooks, настройки плагина.
- **Кто:** ровно один исполнитель с `trusted: true`. Его выбирают при установке из найденных подписочных CLI. Пока он не выбран, настройку меняет только человек через `borsch`.
- **Как:** даже доверенный агент не пишет конфигурацию напрямую. Он создаёт предложение — diff и причину. `borsch config apply` проверяет его по схеме и показывает простыми словами.
  - **Без подтверждения** применяются изменения в сторону строгости: включить более строгий режим, сузить права, отключить пакет.
  - **Только с подтверждением человека, каждый раз и без делегирования:** ослабить режим приватности, добавить внешнего исполнителя, расширить права записи, сменить доверенного агента, установить hooks.
- **Остальные исполнители** только читают: игнорируемая папка `borshkit/` не попадает в worktree (§10.1), а инструменты writer'а ограничены worktree (Claudex `src/adapters.mjs`).
- **Обнаружение обхода:** digest конфигурации входит в `runtimeDigest` (Claudex `src/io.mjs`). `borsch` сверяет его с последним применённым digest из журнала. При расхождении, например после ручной правки или правки нативной сессией агента, jobs не запускаются, пока человек не подтвердит изменение. Запреты в нативных интерактивных сессиях — лишь советующие правила (Claudex `docs/explanation/architecture.md`, «Authority»), поэтому нужна именно проверка, а не только запрет.

### 4.3 Пулы исполнителей и автоматическое переключение при лимитах (D15)

- **Пул** — упорядоченный список исполнителей для класса работ (`image`, `text-review`, `research-summary`…) в `borshkit/settings/pools.json`. Пользователь выбирает состав и порядок. Пример для изображений: Codex → бесплатные API, которые выбрал пользователь.
- **Кандидаты** для пула берутся из реестра исполнителей. Возможности (выход `image`, structured output, лимиты) заполняет probe. Каталог бесплатных API — только подсказка для поиска: он не отмечает модальности и устарел (§1.3).
- **Когда переключаться:** при классифицированном лимите — HTTP 429, `Retry-After`, сообщения квоты. Классификатор QUOTA уже есть в Claudex `src/jobs.mjs:484` [Ф]. Политика пула: `wait-or-switch` (ждать, если `Retry-After` меньше порога, иначе переключиться), `maxSwitches`, порядок.
- **Ограничения, которые переключение не обходит:**
  1. режим приватности — кандидат, запрещённый режимом, пропускается;
  2. capabilities роли;
  3. для ревью — `crossProvider`: если после переключения ревьюер оказался того же провайдера, что и автор, критерий получает UNKNOWN, а не PASS;
  4. ослабить состав пула может только человек (§4.2).
- **Прозрачность:** каждое переключение — строка журнала («лимит у Codex, картинку делает X») и карточка в диспетчерской (§10.3). Фактический исполнитель записывается в доказательство и в метаданные изображения.
- **Переключение пишущей роли посреди задачи (D18).** Перед передачей `borsch` делает точку сохранения в worktree. Новый исполнитель получает тот же контракт, текущий diff и журнал предыдущего, а не его переписку. Каждое сохранение подписано исполнителем: автор коммита — `codex@borshkit`, `claude@borshkit`, `<api-id>@borshkit`. Поэтому `borsch кто-что` (по сути `git blame`/`git log` простыми словами) показывает, кто написал каждую часть. Критерии, проверенные до переключения, остаются действительными, только если digest не изменился.

## 5. Режимы приватности (D2)

| Режим | Что может покинуть машину | Кому | Запрещено | Чем обеспечено |
|---|---|---|---|---|
| **Умеренный** (по умолчанию для открытого кода) | код и документация проекта | любому исполнителю, в т.ч. бесплатным tier'ам с обучением на данных | секреты и ключи, персональные данные | чистая комната, allowlist окружения, фильтр исходящих данных, объявленные PII-пути |
| **Строгий** | ничего, кроме исполнителей с `dataPolicy: no-train` (с источником) или локальных моделей | — | бесплатные tier'ы, исполнители с `unknown` | то же + запрет назначения таких исполнителей в момент назначения |
| **Эксперимент** | всё | любому | — (но ключи обязаны быть одноразовыми) | баннер при старте, журнал ключей сессии, обязательный ручной пункт «ключи отозваны» |

**Механизмы:**
1. **Чистая комната.** Агент работает в worktree или копии, где есть только tracked-файлы и объявленные входы. `.env` и ключи туда не попадают по построению. Для задач вне Git используется копия материалов.
2. **Allowlist окружения.** Claudex запускает провайдеров без опции `env`, поэтому дочерний процесс наследует **всё** окружение родителя, включая секреты [Ф: `src/process.mjs:51`]. Borshkit передаёт только переменные, нужные самому CLI для входа.
3. **Фильтр исходящих данных.** Для API-адаптеров запрос собирает сам Borshkit, поэтому он сканирует весь payload: основа — `inspectBlob` из `src/security.mjs` плюс шаблоны PII. Дальше — блокировка или маскирование и запись в evidence. **Для CLI-агентов так нельзя:** они читают файлы сами. Их защищают чистая комната, deny-правила и sandbox. Какую часть диска может читать Codex в read-only sandbox — [?].
4. **Скан результата** перед любой публикацией (push guard из Claudex).
5. **Переключение режима.** В сторону строгости — в любой момент. В сторону ослабления — только человеком (§4.2). Задача может только ужесточить режим рабочего пространства. Режим виден всегда (§10).
6. **Конец экспериментальной сессии.** Показывается список обнаруженных ключей: имена переменных и места, без значений. Сессия помечена «грязной», пока человек не подтвердит отзыв ключей. Отзыв автоматически не проверить — это ручной пункт приёмки (§6). Артефакты эксперимента не переносятся в проект в умеренном или строгом режиме без повторного скана.

**Сбор из интернета (D16).** Агент Reach отправляет каждую веб-страницу через стороннего посредника Jina Reader (`https://r.jina.ai/<url>`, `agent_reach/channels/web.py:51`), а поиск — через Exa MCP (`https://mcp.exa.ai/mcp`, `channels/exa_search.py`) [Ф]. Значит, адреса и поисковые запросы уходят третьим сторонам.
- *Умеренный режим* — разрешено для публичных адресов.
- *Строгий режим* — посредники выключены: прямое получение страниц, а запросы и адреса, производные от материалов проекта, — только после подтверждения.
- *Эксперимент* — всё.

Cookies и токены площадок (X, Reddit, Xiaohongshu и др.) считаются **секретами**: они не попадают в настройки Borshkit и в чистую комнату. По решению D19 к подключению доступны **все каналы**. Каналы со входом в аккаунт пользователь настраивает сам через Agent Reach — его собственные правила: cookies X только вручную экспортированные, вход в Xiaohongshu не выполняется за пользователя (README) [Ф]. При первом включении канала `borsch` один раз показывает предупреждение: автоматический доступ может нарушать условия площадки, возможна блокировка аккаунта. Согласие записывается в журнал.

По режимам: *умеренный* и *эксперимент* — все настроенные каналы; *строгий* — только публичные каналы, а запросы, производные от материалов проекта, — после подтверждения.

**Публичные данные (D11).** Класс `public-attribution` — имена, ники, ссылки на профили, сайты и страницы поддержки, **опубликованные самими авторами** (README, `FUNDING.yml`, профиль GitHub, `CITATION.cff`). Он разрешён во всех режимах и не считается персональными данными. Не входят: адреса почты из коммитов и всё, что автор сам не выставил публично.

**Остаточный риск, о котором честно сообщается:** поиск PII по шаблонам даёт пропуски. Гарантия распространяется только на объявленные пути и распознаваемые форматы. Если у проекта `containsPersonalData: unknown`, в листе приёмки появляется ручной пункт.

## 6. Приёмка по целям пользователя: автоматическая или смешанная (D3, D10)

| Класс критерия | Кто решает | Итог |
|---|---|---|
| `auto` | детерминированная проверка, привязанная к текущим digest: тесты, сборка, lint/typecheck, воспроизводимость сборки, схема, существование и дословность цитат, readback сохранения через CLI хоста в тестовом хранилище, чистый скан исходящих данных | **PASS/FAIL автоматически** |
| `model` | модель-ревьюер (по возможности другого провайдера) | FAIL с воспроизводимым доказательством (file:line + как воспроизвести) автоматически возвращает задачу на исправление. PASS модели закрывает критерий **автоматически, только если для этого типа критерия достигнута цель пользователя по качеству** (например, «доля ложных PASS ≤ X% на наборе оценки», §17). Пока цель не подтверждена измерением, PASS модели — ручной пункт «модель утверждает X — проверь в file:line» |
| `manual` | человек | внешний вид, UX, работа на реальном устройстве, соответствие утверждений отчёта источникам, юридические вопросы, отзыв ключей после эксперимента |

**Цели приёмки (D10)** — раздел контракта, который заполняет пользователь (готовые шаблоны есть у профилей):
- *цели результата* — что должно быть достигнуто, с измеримым признаком (тест, метрика, порог, наблюдение);
- *политика приёмки* — `auto` (принять, как только достигнуты все цели), `mixed` (автоматика + ручные пункты) или `manual`;
- *цели доверия* к `model`-критериям — порог качества, при котором PASS модели закрывает критерий без человека.

Если цели достигнуты и все проверки CURRENT, задача принимается автоматически, а решение записывается с указанием, какие цели и доказательства его обосновали. Если цель неизмерима, `task check` предупреждает об этом до начала работы и переводит цель в ручной пункт.

- UNKNOWN любого класса становится ручным пунктом с причиной. Автоматического PASS у него не бывает.
- **Статусы задачи:**
  - «принято»: цели достигнуты, все автоматические критерии PASS, ручные пункты (если есть) подтверждены;
  - «автоматически ок, ждёт тебя»;
  - «нужно исправить»: есть FAIL;
  - «не проверено».
- **Ручной пункт** содержит: что проверить (одна фраза), шаги, что должно быть видно, где смотреть, почему это не автоматизировано, ссылки на уже собранные доказательства. Формат — Markdown и локальный HTML. Подтверждение `borsch принять <задача> --пункт <id> ok|fail "заметка"` привязывается к digest; если исходники потом меняются, подтверждение устаревает.
- `task check` ещё **до работы** показывает, сколько критериев уйдут в ручную приёмку: слепая зона видна заранее (расширение `analyzeContract`).

## 7. База знаний проекта вместо Graphify: заметки + wikilinks + SQL (D6, D9)

**Назначение:**
- контекст-пакеты для агентов;
- **обучение для всех (D9)** — люди читают и редактируют граф в **Obsidian**, агенты получают срезы контекста, все пользуются одним источником. Дообучение моделей в задачу не входит;
- самоподдержка: факты пересчитываются при изменениях, устаревшие не выдаются.

**Модель данных:**
- *Узлы:* файл, раздел документа, символ, решение (ADR), задача, критерий, доказательство, урок, материал, внешняя ссылка.
- *Рёбра:* `imports`, `defines`, `references`, `documents`, `implements`, `tests`, `decided-by`, `verified-by`, `supersedes`, `learned-from`.
- *Атрибуты каждого факта:* `provenance: EXTRACTED|IMPORTED|INFERRED|DECLARED`, источник (`extractor@version`, `model@version` или человек), `sourceDigest` файлов.
- Факт действителен, пока совпадают digest. **Это та же семантика CURRENT/STALE, что у доказательств**: база знаний и evidence store — одно хранилище.

**Формат «заметки + wikilinks + SQL» (D9), версия v1 — `docs/kb-format.md`:**
- **Источник истины — хранилище Obsidian** `borshkit/` в корне проекта (§10.1); знания лежат в `borshkit/knowledge/`. Каждая сущность — Markdown-заметка с YAML-frontmatter (Obsidian Properties):
  ```yaml
  ---
  bk-type: module          # concept | decision | lesson | module | task | source | project | person | role
  bk-id: src/core/converge.mjs
  bk-provenance: EXTRACTED # EXTRACTED | IMPORTED | INFERRED | DECLARED
  bk-source: kb-js@1
  bk-digest: sha256:…
  implements: ["[[acceptance]]"]
  documented-by: ["[[how-to/acceptance]]"]
  tested-by: ["[[test/converge.test]]"]
  ---
  ```
- **Типизированные связи** — свойства со списками wikilinks; словарь связей фиксирован в `schemas/kb.v1.json`. Wikilinks в тексте заметки — нетипизированная связь `references`.
- **Сгенерированные заметки** (EXTRACTED и IMPORTED — модули, символы, импорты) лежат в `borshkit/knowledge/_generated/` и перезаписываются целиком. Рукописные (DECLARED: понятия, решения, уроки, люди, проекты) генератор не трогает никогда. Код Obsidian как заметки не показывает, поэтому для каждого модуля создаётся заметка-«заглушка» со ссылкой на реальный файл [В].
- **SQL — производный слой:** `borsch kb build` разбирает хранилище и код в `node:sqlite` с FTS5. На Node 22.22.0 это работает без флагов, но печатает ExperimentalWarning [Ф, проверено]. Таблицы: `notes(id,type,path,provenance,source,digest,status)`, `links(src,dst,rel,provenance)`, `fts`. Запросы — только на чтение (`borsch kb sql "SELECT …"`), плюс готовые представления: `stale`, `orphans`, `undocumented_modules`, `decisions_for(path)`. База пересобираема и лежит в `borshkit/.state/`; правят только заметки, не базу.
- **Чтение людьми:** граф Obsidian и группы по `bk-provenance` (выведенное INFERRED визуально отделено), по желанию табличные виды Obsidian Bases. Bases упомянут в профиле Claudex `profiles/obsidian.json` [Ф]. Попадают ли ссылки из свойств в граф Obsidian и как Bases работает со списками ссылок — проверить на E5 [?]. Плагины Obsidian (Dataview и т.п.) не требуются: формат читается как обычный Markdown.
- **GitHub не превращает `[[wikilinks]]` в ссылки** [В]. Для публичной документации — `borsch kb export --github`: копия с относительными ссылками в `docs/` проекта (сама папка `borshkit/` игнорируется, D13).
- **Путеводители:** заметки `start-here`, «понятия → модули → решения» для людей; для агентов — `borsch context`.

**Слои извлечения:**

| Слой | Что | Чем | В MVP |
|---|---|---|---|
| K0 | инвентарь файлов и хэши; Markdown (заголовки, ссылки, упоминания путей и символов в коде, frontmatter); манифесты (`package.json`, Obsidian `manifest.json`); импорты JS/TS; контракты, доказательства, решения Borshkit | собственный код без зависимостей; для TS — `typescript` проекта, если он уже установлен | да |
| K1 | точные мультиязычные индексы | **импорт** стандартных форматов от поддерживаемых внешних инструментов: SCIP, universal-ctags JSON, metafile сборщика (как `graph trace` в Claudex); выбор — в уточняющей сессии | после MVP |
| K2 | смысловые связи документ↔код, резюме | job модели; хранятся отдельно, **никогда не являются доказательством приёмки**; человек может повысить до `DECLARED` | после MVP |

**Самоподдержка:**
- инкрементальная переиндексация на командах `borsch`, по желанию — git post-commit hook;
- **уроки создаются только из принятых задач, postmortem и решений**, не из транскриптов: это совместимо с режимами приватности;
- если связанные с уроком пути изменились, урок помечается «проверить актуальность», а не удаляется.

**Контекст для задачи — `borsch context <задача>`.** Это срез по путям контракта: описывающие документы, решения, уроки, тесты, недавние сбои; размер ограничен. Порядок: CURRENT EXTRACTED > DECLARED > IMPORTED > INFERRED, устаревшее не выдаётся. Это требование Claudex «old graph facts must not outrank current files» (`docs/research/validation.md`).

**Не строим:** собственный мультиязычный AST-парсинг (tree-sitter требует нативных модулей — это ломает принцип «без зависимостей» и неподъёмно для одного сопровождающего); векторную базу в MVP. Сначала FTS5. Удалённые embeddings означают, что данные покидают машину, поэтому их доступность зависит от режима приватности.

## 8. Команда ролей полного цикла (D12)

**Роль** — это файл `roles/<id>.json`, а не отдельный агент:
- назначение;
- этап;
- права (`read-only|workspace-write`);
- **требуемые capabilities** исполнителя: модальности, structured output, sandbox;
- скиллы (пакеты);
- **собственные проверки и цели приёмки**;
- требование `crossProvider` (ревью от другого провайдера, чем у автора).

Роль назначается на исполнителя по манифесту (§4). Если ни у одного исполнителя нет нужной capability, роль недоступна и в статусе об этом сказано прямо. Профиль и задача включают только нужные роли: определение роли ничего не стоит, а запуск стоит. Каждая роль проходит абляцию (§17).

| Этап | Роль | Что делает | Источник | Модальности | В MVP |
|---|---|---|---|---|---|
| План | `configurator` | настраивает среду через предложения | D1 | текст | да |
| План | `architect` | контракт, цели приёмки, наименьшее связное изменение | Claudex `architect` | текст | да |

**Ponytail как «ленивый сеньор» — как подключать.**

Что он даёт [Ф]: промпт с «лестницей» — не нужно → уже есть в коде → stdlib → платформа → установленная зависимость → одна строка → минимум. Плюс оговорки: проверки на границах доверия, обработку ошибок, безопасность и доступность не упрощать; сначала понять задачу. И ревью-режим (`skills/ponytail/SKILL.md`, `skills/ponytail-review/SKILL.md`).

Как ставить:
- Подключаем **только тексты скиллов** с пином `552acd5`, MIT, с указанием автора.
- **Hooks не ставим.** `hooks/claude-codex-hooks.json` вешает его на `SessionStart`, `SubagentStart` и `UserPromptSubmit`, а промпт требует «ACTIVE EVERY RESPONSE» [Ф]. Это сделало бы его глобальным для всех ролей, включая документацию и исследования. В Borshkit линза вставляется только в пакеты `implementer` и `simplicity-reviewer`.
- **Контракт главнее линзы.** Проверки и цели проекта не «упрощаются»; Ponytail сам запрещает упрощать то, что явно запрошено.

Что известно о его цифрах [Ф]:
- Цифры README («~54% меньше кода, ~20% дешевле, ~27% быстрее, 100% safe») получены на 12 задачах, Haiku 4.5, n=4. LOC — это добавленные строки `git diff`.
- По словам авторов, «we do not run a server or a browser… we measure the code» (`benchmarks/results/2026-06-18-agentic.md:67-69`), то есть **работоспособность фич не измерялась**.
- «Safe» — это 20/20 прогонов на 5 задачах безопасности.

Поэтому включать линзу по умолчанию стоит только после нашей абляции, где мерится приёмка, а не только LOC.

**Проверки ролей подачи (класс `auto`):**
- все изображения существуют и имеют alt-текст;
- размер не выше лимита профиля;
- при использовании `<picture>` есть светлый и тёмный варианты;
- ссылки и бейджи открываются (если позволяет режим);
- для каждого сгенерированного изображения записаны модель, промпт и дата;
- нет чужих логотипов без разрешения правообладателя.

Внешний вид проверяет человек (`manual`).

### 8.1 `researcher` и Agent Reach (D16)

Что это [Ф]:
- MIT, версия 1.5.0, Python ≥ 3.10, около 7,3 тыс. строк кода; 376 коммитов с 2026-02-24.
- Это **установщик, диагностика и маршрутизатор**: читает и ищет не он сам, а сторонние инструменты — OpenCLI, yt-dlp, twitter-cli, bili-cli, rdt-cli, mcporter, gh (`agent_reach/core.py`, `docs/install.md`). В его CLI нет команды «прочитать»: есть `setup`, `install`, `configure`, `doctor`, `skill`, `format`, `transcribe`, `watch` и др. (`agent_reach/cli.py:77-186`).
- 16 площадок. Без настройки работают: веб через Jina Reader, YouTube, RSS, V2EX, GitHub для публичного чтения. Поиск — через Exa MCP. Остальное требует входа в аккаунт.
- Установка рассчитана на то, что агент сам скачает `docs/install.md` из ветки `main` и выполнит её. Безопасный по умолчанию режим только проверяет машину, а `--system` ставит системные зависимости.

Как подключаем [В]:
1. **Версия фиксирована.** Установка — предложение `configurator`, которое подтверждает человек (§4.2). Никаких «прочитай инструкцию из main и выполни», никакой автоматической проверки обновлений (`watch`, `check-update`).
2. **Skill Agent Reach даёт `researcher` знание маршрутов**, но описание skill требует «MUST USE» при любом URL. Поэтому, как и Ponytail, он подключается только к роли `researcher`, а не глобально.
3. **Захват источников — обязанность Borshkit.** Каждое полученное содержимое регистрируется в материалах (§12): `borsch fetch <url> [--via web|youtube|rss|github|search]` вызывает выбранный инструмент, сохраняет копию, sha256, время, канал и бэкенд. Если агент прочитал источник в обход `borsch fetch`, ссылка на него в отчёте не проходит проверку цитат (`auto`) — так захват становится обязательным без контроля самого агента.
4. **Каналы (D19):** при установке `agent-reach doctor --json` даёт список всех 16 площадок с состоянием: «работает», «нужна настройка», «недоступно». `borsch` предлагает настроить каждую, но не делает этого за пользователя.
5. **Получение — на стороне `borsch`, а не агента.** Агент `researcher` не видит cookies и токены. Ему разрешены только команды `borsch fetch …` и `borsch search …` — для Claude Code это правило разрешений вида `Bash(tw fetch:*)` (синтаксис проверить на E4 [?]). Сами вызовы инструментов Agent Reach выполняет процесс `borsch` с нужным окружением, а агенту отдаёт сохранённую копию. Так все каналы доступны, но секреты не попадают в чистую комнату.
6. **Состояние каналов** (`agent-reach doctor --json`) показывается в диспетчерской (§10.3).
5. **`agent-reach doctor --json`** показывает доступность каналов на экране «Где мы».

## 10. Развёртывание «как мод» и прозрачность (D8)

**Поставка:**
- `borsch` — единственный движок (npm-пакет или архив, Node ≥ 22).
- Тонкие «лица»:
  - **плагин Claude Code**: skills, команды, минимальные hooks, `userConfig`; формат подтверждён рабочим примером ECC `.claude-plugin/plugin.json` с `userConfig.hooks_enabled` [Ф];
  - **`AGENTS.md` + каталог skills** для Codex и других агентов (формат Agent Skills).

**Принципы «понятно даже ребёнку»:**
1. Один экран «Где мы»: задача → кто работает → что можно трогать → режим приватности → что проверено → что ждёт тебя.
2. Четыре состояния — цвет и слово: зелёный «проверено», жёлтый «ждёт тебя», серый «не проверено», красный «надо исправить».
3. Журнал простыми фразами: «Claude изменил 3 файла в `src/` по задаче „X“; тесты прошли».
4. Перед рискованным действием (запись, отправка данных наружу, ослабление режима, установка) — одна фраза объяснения и вопрос.
5. Команды — глаголы на языке пользователя (`borsch начать | статус | проверить | принять`) с английскими синонимами [В — обсудить в сессии].
6. Строка статуса в Claude Code показывает режим и статус задачи. Механизм реально используется — ECC `scripts/hooks/ecc-statusline.js` [Ф].
7. Карта проекта из базы знаний — локальный HTML без сервера.
8. Старт без настройки: профиль определяется автоматически, работа возможна в папке без Git.

Проверяемость прозрачности: юзабилити-тест (§17) — новичок проходит сценарий и своими словами объясняет текущий статус. Считаются вопросы и ошибки.

### 10.1 Локальный запуск: папка `borshkit/` в корне проекта (D13)

```
<проект>/
├─ borshkit/            ← одновременно хранилище Obsidian; автоматически в gitignore
│  ├─ START-HERE.md      путеводитель: где что лежит, что делать дальше
│  ├─ settings/          workspace.json, roles/, pools.json, executors.json (без секретов)
│  │  └─ settings.md     сгенерированное зеркало настроек простыми словами (только чтение)
│  ├─ knowledge/         заметки (§7), _generated/
│  ├─ tasks/<id>/        contract.json, лист приёмки .md, доказательства, журнал
│  ├─ materials/         content-addressed копии источников
│  ├─ journal.md         события простыми фразами
│  └─ .state/            index.sqlite, блокировки, кэш (пересобираемо)
└─ .gitignore            + строка `/borshkit/` с пометкой `# Borshkit local workspace (auto)`
```

- **`borsch init`** создаёт папку и идемпотентно дописывает правило в `.gitignore` (создаёт файл, если его нет). Вариант `--local-only` пишет правило в `.git/info/exclude`, не трогая отслеживаемые файлы. Для папки вне Git правило не нужно. Имя папки настраивается.
- **`borsch doctor` и каждая запись** проверяют `git check-ignore borshkit/`. Если папка не игнорируется, запись доказательств запрещена: иначе состояние попадёт в коммит и в digest исходников.
- **Совместимость с ядром Claudex.** Claudex требует, чтобы состояние было вне checkout: `assert(!inside(repo,ws.state), 'Task state must be outside the source checkout')` в `src/tasks.mjs` [Ф]. `snapshot()` берёт файлы через `git ls-files --others --exclude-standard`, а значит игнорируемые файлы в digest не входят (`src/io.mjs`) [Ф]. Правило заменяется на «состояние только в игнорируемой папке». Тест на E3: запись в `borshkit/` не меняет digest исходников.
- **Worktrees** остаются **вне** проекта, рядом (`../<проект>.borshkit-worktrees/`), как в Claudex. Git не переносит игнорируемые файлы в worktree, поэтому писатели не видят `borshkit/settings` — чистая комната сохраняется. Нативная сессия агента в корне проекта настройки видит и может прочитать. Секретов там нет; правка без `borsch` обнаруживается по digest (§4.2).
- **Секреты в `settings/` запрещены.** Ключи хранятся в переменных окружения или хранилище учётных данных ОС, в настройках — только имена. `borsch` отказывается записать значение, похожее на ключ (сканер из `src/security.mjs`).
- **История пространства (D17).** Внутри `borshkit/` — отдельный локальный git-репозиторий, без remote по умолчанию. Git проекта его не видит: папка игнорируется. Он хранит историю настроек, знаний, задач и листов приёмки и даёт `snapshot()` для выходов вне Git (§12). Работа с ним — только через оболочку §10.2. Публикация документации — `borsch kb export --github` в `docs/` проекта.
- Obsidian, скорее всего, скрывает папки с точкой внутри хранилища [?], поэтому имя папки без точки.

### 10.2 Оболочка Git для новичка (D17)

Цель: человек, который никогда не слышал о Git, может безопасно сохраняться, смотреть изменения и откатываться — и постепенно понимает, что происходит.

**Два репозитория, объяснённые одной фразой** — на экране «Где мы» и в `START-HERE.md`:
- «**История проекта** — код и документы. Её можно отправить на GitHub, но только после твоего «да»»;
- «**История пространства** — твои настройки, знания и проверки. Она никогда не покидает компьютер».

**Словарь** (режим «новичок» по умолчанию; режим «знаю Git» показывает настоящие термины):

| Что видит новичок | Что делает `borsch` | Git под капотом |
|---|---|---|
| «Сохранить точку возврата» | снимок с понятной подписью | `git add` + `git commit` |
| «Что изменилось?» | список файлов + одна фраза на файл + цветной diff по запросу | `git status`, `git diff` |
| «Кто это сделал?» | автор каждого изменения: человек или исполнитель | `git log`, `git blame` |
| «Вернуть как было» | откат файла или всей задачи; перед этим автоматически сохраняется текущее состояние | `git restore` / `git revert` — без `reset --hard` |
| «Отдельная копия для агента» | изолированная копия на время задачи | `git worktree` |
| «Черновик» | параллельная версия задачи | `git branch` |
| «Собрать изменения» | перенос принятой работы в основную версию | `git merge`, только после приёмки |
| «Отправить на GitHub» | только по явному «да», с проверкой секретов | `git push` + push guard Claudex |

**Правила безопасности оболочки:**
- никаких разрушающих команд. Force push, удаление веток на сервере и push в защищённые ветки уже запрещает push guard Claudex (`src/security.mjs` `prePush`, тесты в `test/guards.test.mjs`) [Ф]. Запрет `reset --hard` и удаления веток с несобранной работой — новое, пишется в оболочке;
- перед любым «вернуть» и «собрать» — автоматическая точка возврата;
- автосохранения в истории пространства: при приёмке задачи, изменении настроек, каждом переключении исполнителя;
- подписи сохранений человеческие, например «Принята задача „Тёмная тема“: тесты прошли, 2 пункта подтвердил ты».

**Обучение по ходу (постепенное раскрытие):**
- у каждого действия есть «Подробнее»: что произошло простыми словами, картинка-схема из `START-HERE` и настоящая команда Git, которой это сделано;
- заметка `borshkit/knowledge/learn/git.md` с примерами из **этого** проекта: последние точки возврата, кто что менял;
- для папки вне Git `borsch init` предлагает «завести историю проекта» и объясняет, что это даст.

**Что не строим:** собственную реализацию Git и графический клиент. Оболочка — тонкий словарь и правила безопасности поверх установленного `git`, его Claudex уже вызывает через `src/io.mjs` `git()`. Внешние GUI (GitHub Desktop и др.) можно открыть из `borsch`, но объяснения внутри пространства от этого не зависят.

### 10.3 Диспетчерская: фоновый статус «кому ушло, кто работает» (D18)

**Одна модель статуса, четыре вида:**
1. `borsch статус --следить` в терминале;
2. строка статуса Claude Code — одна строка: режим приватности, число активных работ, есть ли что-то для тебя;
3. заметка `borshkit/STATUS.md`, которую `borsch` перезаписывает при каждом событии; открытая в Obsidian, она обновляется сама — Obsidian перечитывает изменённые на диске файлы [В — проверить на E6];
4. локальная страница `borshkit/status.html` с автообновлением, без сервера.

**Карточка работы:**

| Поле | Пример |
|---|---|
| Задача и роль | «Тёмная тема» · пишет код |
| Кому ушло сейчас | Codex (подписка) |
| Состояние | в очереди / думает / пишет файлы / ждёт лимит до 14:20 / передано другому / готово / ошибка |
| С какого времени и последний признак жизни | 14:02 · последнее событие 20 с назад |
| Что делает, простыми словами | «меняет 3 файла в `src/theme/`» |
| История передач | «14:05 Claude упёрся в лимит → передано Codex» |
| Квота | остаток, если провайдер его сообщает; иначе «неизвестно» |
| Что нужно от тебя | «подтвердить 2 пункта приёмки» / ничего |

**Источник данных** — журнал jobs. Состояния, событие готовности провайдера, таймауты и отмена уже есть в Claudex `src/jobs.mjs` [Ф]; к ним добавляются признак жизни (время последнего события провайдера) и события пула (§4.3). Если исполнитель молчит дольше **60 секунд** (D21, настраивается по ролям), карточка показывает «молчит N мин» и задаёт вопрос: подождать, передать другому или остановить. Ответ по умолчанию — «подождать», если последним событием был запуск инструмента (например, идут тесты). Иначе действует политика пула (§4.3). Как на этот вопрос отвечает автопилот — §10.4.

**Уведомления (D21)** — своих звуков и системных уведомлений Borshkit не добавляет: он пользуется механизмом уведомлений основного CLI, в котором работает пользователь (для Claude Code — его собственные уведомления о том, что нужен ввод). Уведомляют только о том, что требует человека: критическая остановка, ручные пункты приёмки, ошибки, исчерпанный пул.

### 10.4 Автопилот, вопросы к человеку и критическая остановка (D21)

**Два режима:** «ручной» — каждый вопрос ждёт человека; **«автопилот»** — рутинные вопросы закрываются ответом по умолчанию. Режим виден в строке статуса рядом с режимом приватности.

**Вопросы делятся на два класса:**

| Класс | Примеры | В автопилоте |
|---|---|---|
| **Рутинный** — обратимое действие с заранее объявленным ответом по умолчанию | исполнитель молчит; ждать лимит или переключиться; выбор из равноценных вариантов в рамках контракта; повторить упавшую проверку один раз | через **60 секунд** без ответа применяется ответ по умолчанию; в журнале: «принято автопилотом по умолчанию», с возможностью отменить через точку возврата |
| **Критический** — необратимое действие, ослабление защиты или слепая зона | всё из «только с подтверждением человека» (§4.2: ослабить приватность, добавить внешнего исполнителя, расширить права записи, сменить доверенного агента, поставить hooks); отправка на GitHub; разрушающие операции Git; согласие с условиями площадки (§8.1); отзыв ключей после эксперимента; превышение бюджета; **ручные пункты приёмки** | **никогда не принимается автоматически**: критическая остановка |

Автопилот отвечает на **вопросы о ходе работы**, а не принимает результат. Приёмка по-прежнему идёт по целям пользователя (§6): автоматически — только то, что закрыто целями и доказательствами, слепые зоны остаются за человеком [В — интерпретация D21; уточнить, если имелось в виду иное].

**Критическая остановка — порядок:**
1. **Блокировка действия.** Hook `PreToolUse` отклоняет действие с причиной (`permissionDecision: deny`). Механизм уже есть в Claudex `src/hooks.mjs:94-112` [Ф]. Для исполнителей без hooks вопрос задаёт сам `borsch` до запуска действия.
2. **Сохранение прогресса.** Точка возврата в копии задачи и в истории пространства (§10.2).
3. **Отчёт** `borshkit/tasks/<id>/stop-report.md` простыми словами: что произошло, почему остановлено, варианты и последствия каждого.
4. **Передача контекста** `handoff.json` + `handoff.md`: контракт, ссылка на текущие изменения, журнал, открытый вопрос, сделанное, следующие шаги. Основа — поля postmortem Claudex: что обещал пакет, где остановился, оставшиеся изменения, что проверить перед повтором (`src/jobs.mjs` `buildPostmortem`) [Ф].
5. **Состояние job — `WAITING_HUMAN`** (новое к состояниям Claudex). Карточка в диспетчерской выделена; уведомление — механизмом основного CLI.
6. **Продолжение — по точному ID задачи**, тем же или другим исполнителем, из `handoff`, а не из «последнего разговора». Это правило восстановления Claudex (`docs/explanation/architecture.md`, «Recovery boundaries») [Ф].

**Риск порога 60 секунд [В].** Модели и долгие проверки (сборка, тесты) могут молчать дольше минуты при нормальной работе. Поэтому молчание во время запущенного инструмента по умолчанию ведёт к ожиданию, а не к переключению. Пороги настраиваются по ролям, и их влияние на ложные переключения меряется на E7.

## 12. Задачи вне Git: идентификация и версии материалов

- **Манифест материалов** (`materials.v1`): `id`, `origin` (путь, URL или «передано пользователем»), `mediaType`, `size`, `sha256`, `capturedAt`. Для URL — ещё `ETag`/`Last-Modified` и **сохранённая копия** в content-addressed хранилище. Доказательство ссылается на копию, а не на живой URL.
- **Digest набора** = sha256 отсортированного манифеста. Новый вход или изменённый байт → новый digest → прежние доказательства и факты базы знаний становятся `STALE`. Версии материалов хранятся в append-only журнале с родителем.
- **Выход** (отчёт и т.п.) лежит в локальном git-репозитории внутри `borshkit/` (§10.1), к нему применим `snapshot()`.
- **Исследования.** Критерий `source` требует ссылку `materialId` + место для каждого утверждения. `checks/citations.mjs` автоматически проверяет существование и дословность цитаты (`auto`). Соответствие утверждения источнику — `model` или `manual`.

## 13. Инварианты

1. `COMPLETED` job ≠ приёмка. Автоматическая приёмка — только когда достигнуты цели пользователя и все решающие доказательства CURRENT. PASS модели решает критерий, только если для его типа подтверждена цель доверия пользователя.
2. Доказательства, факты базы знаний и ручные подтверждения действительны только для тех digest, на которых получены.
3. Отсутствие ответа или проверки → UNKNOWN → ручной пункт, никогда не PASS.
4. Права и режим приватности заданы явно и обеспечены структурно (флаги, чистая комната, allowlist окружения). Hooks — второй, советующий слой.
5. Один координатор. Конфигурацию меняет только доверенный агент через предложения. Ослабление защиты подтверждает только человек.
6. Смена провайдера — записанным решением человека или автоматически внутри пула, разрешённого пользователем и режимом приватности; каждое переключение записано, `crossProvider` не нарушается молча.
7. Состояние пространства — только в игнорируемой папке `borshkit/`; без подтверждённого игнора запись запрещена.

## 14. Своя среда vs «готовая среда + модуль приёмки»

С учётом D4 и D8 целевой продукт — полноценная разворачиваемая среда (вариант B). Порядок сборки при этом сохраняется: **сначала ядро приёмки (вариант A) как фундамент**, затем остальные слои. Каждый слой B — оркестрация jobs, база знаний, пакеты, плагин — остаётся под правилом «оставить или убрать» по итогам сравнения (§17).

Чего собственная инфраструктура по-прежнему не требует:
- tool loop для API-моделей;
- память из транскриптов;
- мультиязычный парсер;
- мульти-агентная оркестрация;
- dashboard-сервер.

## 15. MVP

Первая версия, которой можно пользоваться, — после E1–E3: ядро приёмки, материалы, папка `borshkit/` с оболочкой Git и приватность на одном CLI-исполнителе. Остальное подключается слоями, и каждый слой проходит правило «оставить или убрать» (§14).

**Отложено:** K1 (SCIP/ctags/metafile) и K2 (INFERRED); векторный поиск; tool loop для API-моделей; переключение вне пулов; мульти-агентность, TUI, MCP-сервер; автопубликация; hooks и память ECC; library/emil и HIG; профиль `library` (до этого — `generic` + шаблон проверок); многопользовательская работа; маршрутизация по стоимости; синхронизация истории пространства с удалённым репозиторием; роли `tester`, `adversarial-reviewer`, `flow-auditor`, `release-manager`; hooks Ponytail.

## 17. План сравнения с минимальным baseline

**Варианты:**
- B0 — нативный CLI-агент + `CLAUDE.md`/`AGENTS.md` + проверки проекта + ручная приёмка;
- A — B0 + ядро приёмки;
- B — Borshkit MVP;
- абляции: B без базы знаний; B без ревьюера другого провайдера; B с линзой Ponytail и без неё (мерить **приёмку**, а не только LOC); B без `simplicity-reviewer`; B + один пакет ECC; исследования с Agent Reach (все каналы / только публичные / без него) — полнота и проверяемость источников; переключения для всех ролей включены и выключены — ложные PASS, доля задач с переключением, время до приёмки.

**Задачи:** по каждому профилю — реальные задачи + засеянные дефекты (регресс, «UI показывает успех без сохранения», неверная цитата), засеянные секреты и PII для проверки утечек. Начальное состояние, модели, версии CLI и бюджеты зафиксированы. Порядок прогонов чередуется, оценщик по возможности слеп к варианту. ≥3 повторения — пилот, не статистика.

**Метрики:**
- *Подтверждённое качество.*
- *Ложные PASS*, в т.ч. отдельно по классу `model`: по ним проверяются цели доверия пользователя.
- *Избыточные UNKNOWN/ручные пункты* — цена осторожности.
- *Время* до приёмки и активное время человека, включая время на лист ручной приёмки.
- *Расход моделей* — токены, tool calls, повторы, стоимость или квоты; лимиты подписок отдельно.
- *Ручные вмешательства.*
- *Утечки* — засеянные секреты или PII, покинувшие машину (цель — 0).
- *База знаний* — precision/recall и влияние на метрики задач (абляция).
- *Понятность* — результаты юзабилити-теста.
- *Атрибуция* — найденные засеянные пропуски благодарностей и лицензий (цель — все).
- *Размер изменений* — LOC diff как вторичная метрика, только вместе с приёмкой.
- *Сопровождение* — строки собственного кода, внешние пины, часы на синхронизацию, поломки при обновлениях CLI.

**Правило решения (фиксируется заранее):** вариант с ростом ложных PASS или с любой утечкой отклоняется. При равенстве остальных метрик выбирается вариант с меньшим сопровождением.

## 18. Риски, неизвестные, оставшиеся вопросы

**Риски:**
- **объём вырос**: база знаний, приватность, мод и прозрачность при одном сопровождающем — главный риск, поэтому строгий порядок этапов и правило «оставить или убрать»;
- дрейф флагов CLI;
- экспериментальный статус `node:sqlite`;
- пропуски PII-детекции;
- защита CLI-агентов держится на чистой комнате, а не на фильтре трафика;
- «усталость от ручных пунктов» и формальное подтверждение;
- база знаний подсовывает устаревшее или выведенное как факт;
- скорость изменений ECC и неоднородность лицензий;
- устаревание каталога API;
- разрастание числа ролей без измеренной пользы;
- глобальная активация Ponytail при параллельной установке его плагина;
- сгенерированные изображения: права, чужие бренды, вес репозитория;
- GitHub не показывает wikilinks — две формы одной документации;
- Agent Reach: установка «агент сам выполняет инструкцию из main» — риск цепочки поставок, поэтому только фиксированная версия; условия использования площадок; передача адресов и запросов посредникам (Jina, Exa); Python и сторонние CLI вне принципа «без зависимостей»;
- бесплатные API в пулах: разное качество, обучение на данных, исчезновение лимитов без предупреждения;
- локальный git пространства без remote теряется вместе с диском — нужна резервная копия (вопрос ниже);
- переключение пишущей роли посреди задачи: разные стили и неполная передача намерений; смягчается контрактом, точкой сохранения и журналом, проверяется оценкой;
- все каналы Agent Reach: риск блокировки аккаунтов и нарушения условий площадок лежит на пользователе — это фиксируется его согласием, но не устраняется;
- оболочка Git может скрыть важное от опытного пользователя — поэтому есть режим «знаю Git» и «Подробнее» у каждого действия.

**Неизвестно:** тесты ECC на `ef648e0`; границы чтения Codex read-only sandbox и его флаги; судьба `cheahjs/free-llm-api-resources`; поддержка отключения телеметрии в CLI; реальный вклад скиллов и базы знаний на задачах владельца.

**Блокирующих вопросов для этапов E0–E3 нет.**

**Открыто для обсуждения на GitHub (D20):** нужна ли резервная копия истории пространства — приватный remote, облачная папка или ничего. Обсуждение открывается в репозитории проекта после его переименования. Для GitHub Discussions их нужно включить в настройках репозитория. До решения резервной копии нет, и это записано в рисках.

**Проверить при случае (не блокирует):**
1. Верна ли интерпретация D21: автопилот отвечает только на рутинные вопросы о ходе работы, а слепые зоны приёмки остаются за человеком?
2. Короткая команда `borsch` устраивает, или оставить только `borshkit`?

## 14. Операционная архитектура 0.12.0

Дополнение к исходной проектной спецификации: [операционное руководство](guide/team-operations.md) и [контроль модернизации](discussions/modernization-2026-10-09.md) описывают текущие контракты, ограничения и статус поставки.

- Роль отделена от модели, harness и transport. Контракт/fixtures → конкретная модель → схема → независимые проверки → квалификация; PASS набора не является приёмкой проекта.
- `execution` резервирует совокупные tokens/USD и WIP под общей блокировкой; UNKNOWN после обрыва не снимается автоматически. Сравнение стоимости допускается при актуальных тарифах и одном SHA набора. Жёсткий счёт ограничивает провайдер.
- `dependencies` — DAG; запуск ждёт принятого и интегрированного состояния. Checkpoint фиксирует снимок, не общий release PASS.
- Для настроек и критических вопросов допускается отдельный WebAuthn ES256 протокол: первоначальное доверенное сопряжение, UV/UP, origin/RP, проект и ревизия, nonce, expiry, отзыв и внешний аудит. Терминальная фраза остаётся UX-барьером; реестр/сервис вне полномочий агента необходимы для границы доверия.
- Монитор запускается явно, ограничен циклами, читает наблюдения и создаёт предложения. Настройки, оплачиваемые вызовы, jobs и автопилот не запускаются монитором.
- Gemini CLI/API имеют собственные профили; VS Code — локальный runtime/команды; Copilot/Roo/Cline — инструкции, без заявленного native executor. Remote Control и голос предоставляются host, возможности transport не переносятся автоматически.
- Capsule переносит явные исходники, не credentials, probes, принятие или активную сессию. Checksum отдельно от GitHub OIDC attestation. Linux/Windows/macOS подтверждаются CI точного commit; одинаковый вывод модели не обещается.
