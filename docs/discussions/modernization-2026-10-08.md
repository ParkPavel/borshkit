# Аудит и программа модернизации — 2026-10-08

Основание — пользовательская обратная связь в чате и чтение реализации 0.11.1. Это аудит архитектуры и исходного кода, не независимый pentest, не сертификация безопасности и не живое сравнение моделей. Изменения первого этапа перечислены отдельно; остальные требования сохраняются открытыми.

## Что уже хорошо устроено

Роли отделены от исполнителей; есть явные пулы, доказательства привязаны к состоянию, писатель работает в worktree, импортированное ревью не закрывает приёмку само, все семейства незавершённых авторов учитываются. Ядро без runtime-зависимостей, упаковка плагином/CLI/архивом, тесты на fake исполнителях и CI Linux/Windows дают основу для развития.

## Найденные разрывы и первый этап

| Приоритет | Наблюдение 0.11.1 | Изменение / открытая работа |
|---|---|---|
| Высокий | help/version или `/models` трактуются пользователем как готовность команды; качество роли не подтверждено | каталог разделяет пробу подключения и оценку роли; оценки с моделью, сроком и отпечатками |
| Высокий | полный снимок старого предложения мог перезаписать новые настройки | `baseDigest`, блокировка операций и отказ при изменении зависимостей |
| Высокий | план распределения и резерв ревью отсутствуют | объяснимые планы, резерв семейства для ревью, учёт всех writer fallback |
| Высокий | ошибка `command --version` подавлялась, проба могла стать успешной | ошибка делает пробу FAIL |
| Средний | пробы без привязки к конфигурации и срока | fingerprint и часовой срок пробы; старые пробы требуют обновления |
| Средний | остатки API не имеют общих единиц, области и актуальности | отдельные наблюдения; `/models` отделён от генерации; неизвестное явно |
| Средний | `готово` работы легко спутать с приёмкой | диспетчерская отдельно поясняет завершение выполнения и приёмку; сохраняет модель и свидетельство запуска |
| Средний | флаг повторной попытки исчезал с новой attempt | не более одного ожидания Retry-After на исполнителя в работе |
| Высокий | опросы мониторинга могли перекрываться при медленной записи и терять ответ об остановке, выявлено CI Windows | последовательные опросы, ожидание текущего опроса при завершении работы; проверка единственного вопроса |
| Высокий, открыто | подтверждение ослабления только через терминал | защищённый удалённый канал спроектирован, реализация и аудит впереди |
| Средний, открыто | нет последовательного мастера onboarding | текущий безопасный пустой каталог; мастер безопасности/сред/ролей — следующий этап |
| Средний, открыто | независимые клиенты имеют разные инструкции, плагины и Remote Control | матрица границ поддержки; нативные адаптеры Gemini/IDE — следующий этап |
| Средний, открыто | нет управляемого фонового сервиса и измеренной оптимизации | локальные снимки и явный watch; демон, WIP, бюджеты и прогнозирование — следующий этап |

`PASS` импортированной оценки остаётся заявлением человека. Объявленный `provider` остаётся заявлением о семействе модели. Нет гарантии неизменности внешней модели за alias, криптографической аттестации отчёта или обязательного резерва ревью для ручных запусков вне нового плана. Нельзя объявлять эти ограничения устранёнными.

## Практики сильных IT-команд

Профессионализм выражается в проверяемом процессе: ясное владение результатом, маленькие изменения, видимое ограничение незавершённой работы, независимая проверка, воспроизводимый build, своевременная интеграция и документация решений. Эти принципы переносим на агентские роли; это инженерная рекомендация, а не утверждение, что исследован объективный рейтинг «лучших пулов».

- DORA: наблюдать поток поставки и стабильность, а не количество агентских сообщений. [Модель способностей](https://dora.dev/capabilities/).
- Google Engineering Practices: небольшие проверяемые изменения, цель ревью, ответственность автора и ревьюера. [Code review](https://google.github.io/eng-practices/review/).
- Google SRE: наблюдаемость должна помогать действовать; сигнал состояния важнее объёма логов. [Monitoring distributed systems](https://sre.google/sre-book/monitoring-distributed-systems/).
- NIST SSDF: требования безопасности, защита среды и артефактов, проверка выпуска, реагирование на дефекты. [SSDF](https://csrc.nist.gov/projects/ssdf).
- SLSA: происхождение сборки и воспроизводимость цепочки, без обещания детерминированного вывода LLM. [Specification](https://slsa.dev/spec/).
- Dev Containers: декларация среды снижает расхождения машин; контейнер не означает поддержку любого телефона. [Specification](https://containers.dev/implementors/spec/).

## Источники по интеграции сред

Первичные источники собраны через Firecrawl; интерфейсы меняются, поэтому при реализации адаптера нужно снова сверить актуальную документацию и закрепить версию. Ссылки являются источниками решений, тексты и код из них не импортированы в пакет.

| Источник | Вывод для Borshkit |
|---|---|
| [AGENTS.md](https://agents.md/) и [Agent Skills](https://agentskills.io/specification) | общие инструкции и применимый навык — разные уровни; загрузка материалов по необходимости |
| [Claude Code plugins](https://code.claude.com/docs/en/plugins) | упаковка включает навыки, хуки, агенты и MCP; права локальной среды остаются её ответственностью |
| [Claude Remote Control](https://code.claude.com/docs/en/remote-control) | удалённое управление требует поддерживаемого сценария и живого процесса исполнения |
| [Codex remote connections](https://learn.chatgpt.com/docs/remote-connections) | учитывать возможности и условия конкретного приложения; не переносить их автоматически на CLI |
| [VS Code agent customization](https://code.visualstudio.com/docs/agent-customization/overview) | конфигурации разных harness не эквивалентны автоматически |
| [Gemini CLI IDE integration](https://geminicli.com/docs/ide-integration/) | companion и контекст IDE требуют собственного адаптера |
| [Roo Code](https://docs.roocode.com/) и [Cline](https://docs.cline.bot/) | конкретные средства и правила доступа проверяются отдельно |
| [MCP specification](https://modelcontextprotocol.io/specification) | согласовывать версию; транспорт не является sandbox или доказательством согласия |
| [ACP](https://agentclientprotocol.com/protocol/overview) | мультимодальные возможности клиента согласовываются; не считать их универсальными |
| [CloudEvents](https://github.com/cloudevents/spec/tree/v1.0.2) | envelope события, идентичность source/id; exactly-once не гарантируется |
| [WCAG status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | изменения состояния должны читаться без догадок по цвету |
| [OWASP prompt injection](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) | внешние данные не должны получать полномочия; текстовые метки недостаточны |

Выбор модели опирается на [OpenAI model selection](https://developers.openai.com/api/docs/guides/model-selection), [rate limits](https://developers.openai.com/api/docs/guides/rate-limits), [image generation](https://developers.openai.com/api/docs/guides/image-generation), [Gemini image generation](https://ai.google.dev/gemini-api/docs/image-generation) и [официальную карточку Llama](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E-Instruct). Эти источники описывают свойства и способы оценки, но не доказывают универсальный рейтинг пригодности для проектных ролей.

## Последующие этапы и критерии готовности

1. **Первый этап — прозрачная команда и ресурсы.** Пробы/оценки/квоты различаются, изменения данных блокируют старые предложения, есть команды и документация, fake тесты. Живое качество моделей не заявлено.
2. **Onboarding и оценки.** Мастер не делает платных вызовов без ясного действия пользователя; стенд одинаковых заданий, воспроизводимые отчёты, условные рекомендации моделей, бюджет.
3. **Адаптеры и мобильное управление.** Отдельная матрица версий/прав/Remote Control, согласованный вход файлов/изображений/текста, защищённое удалённое подтверждение с тестами replay/expiry/revision/revocation.
4. **Длительная командная работа.** Ограничение WIP, координация интеграции, checkpoints, управляемый мониторинг, безопасная остановка и восстановление, доказанные источники квот.
5. **Переносимая поставка.** Проверенный архив и checksum, подписанная provenance по выбранной схеме, примеры воспроизведения на Linux/Windows/macOS, инструкции просмотра с телефона, обновление README и схем одновременно с выпуском.
